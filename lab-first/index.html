Build the lab first

The most useful thing I built for my VR game this month wasn't a feature. It was a small throwaway page that let me decide what a feature should feel like before anyone built it.

The problem was the loop, not the work

Combat in The Old Gods felt choppy. Fixing it meant changing a number, putting a VR headset on, finding a fight, watching one sword swing, taking the headset off, and describing what felt wrong. Then again. I was judging differences of tens of milliseconds through a loop that cost minutes each time.

That shape shows up everywhere. Whenever checking your work is slow, expensive or needs other people, you end up making fewer, bigger, worse decisions.

The pattern

  1. Research first. Find how the best people in the field think about it. For me that was Disney's twelve principles of animation, fighting-game hitstop and Riot's effects style guide.
  2. Name the primitives. Boil the thing down to the few parts everything is made of. Every attack turned out to be five beats: gather, launch, travel, impact, aftermath.
  3. Build a quick lab. One page, one control per primitive, real constraints baked in. Mine uses the game's real character proportions.
  4. Compare against today. A before and after toggle on the same screen. Flipping it is what made the problem obvious in one second.
  5. Approve. Lock in the numbers in a form the real build reads directly, so nothing gets lost in translation.
  6. Build it once. The final build becomes a translation of agreed decisions, not more exploration. The expensive check happens once, at the end.

Why it works

  • Decisions get cheap. A change in the lab costs a second. A change in the real thing costs a build and a check.
  • You argue about the parts, not the whole. "It feels off" is hard to act on. "The hold is two frames too short" is easy.
  • Small sections stay editable. Each primitive moves on its own, so you can fix one beat without reopening everything else.
  • The lab is a shared language. Once the primitives have names and numbers, anyone can reason about them, including an AI building the final version.
  • It's disposable. The lab doesn't need to be good software. It needs to make one decision easy, then it can go.

For me, nine attacks went from "feels choppy" to approved in under an hour, and I never put the headset on.

It isn't about games

Any time a check is slow, a lab can come first. A few places the same move applies:

Building a lab with Claude

The lab doesn't need an engineer or a project. I describe the decision I'm trying to make and Claude builds the page. The ask that works for me looks roughly like this:

Research how experts approach [the thing]. Then build me a single-page lab for it: - one control for each core primitive, with the expert starting values - a before/after toggle against how we do it today - a view that matches what the real user actually sees - real-world references for each part, so I don't have to dig - an approve button that saves the agreed numbers for the real build

Then I play with it, approve, and only then does the real build start. This is now the default way I work on anything where I'd otherwise be guessing.
